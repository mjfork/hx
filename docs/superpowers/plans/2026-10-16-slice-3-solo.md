# Slice 3: Solo Sessions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `hx start <root>` on a root with no open children opens a Space, and its tab 1 runs one solo Claude session. That session works the ticket through the trk gates with the eng-toolkit skills, and the watcher closes the Space when the root closes.

**Architecture:**
- `hx start` gains the launch inputs: model, effort, reason and parent. It also gains the load guard, a worktree and background dependencies, and a dry run.
- The launch inputs are stored in the binding, and the watcher's session map copies them into `sessions.jsonl`.
- A new user-level skill, `/hx-work`, is the session's script. It calls the eng-toolkit skills at the gates and opens asks through trk.

**Tech Stack:** Python 3.12, pytest, the trk CLI, the herdr CLI, and bash helpers in `~/.local/bin`.

**Spec:** `docs/superpowers/specs/2026-10-11-herdr-extension-design.md`. Read Section 2, and amendments 2, 3, 5 and 6. Scope agreed with sme-herdr-env (hx-s3-scope-1, 2026-10-16) and approved by Michael on 2026-10-16.

## Global Constraints

- Tests never touch the live trk store (use the `trk_home` fixture) or live herdr (use `FakeHerdr`). Tests never run `launch-guard.sh` or `ticket-deps.sh`; inject fakes instead.
- The plugin writes to trk only `claim release` and `sweep` as actor `herdr`. The solo session writes to trk as itself.
- Commit messages carry no `Co-Authored-By` and no "Generated with" lines.
- Temporary files go in `tmp/`.
- Work in a worktree: `git worktree add ../herdr-extension-slice3 -b slice-3-solo`, with its own `.venv`. The service runs the code checked out in `main`.
- Model default `claude-sonnet-5-5` (amendment 3). Effort default `medium` (routing-1: sonnet/medium).
- Effort must be one of `low|medium|high|xhigh|max`. Model must match `^[][A-Za-z0-9._-]+$` (the same rules as dispatch-ticket.sh).
- A model containing `opus`, in any case, needs `--reason` (routing-1: "Choosing opus for a child needs a one-line reason").
- `sessions.jsonl` rows keep the amendment 6 shape: `parent`, `effort` and `reason` are added, and no field is renamed.
- Launch-guard contract (sme-herdr-env):
  - `launch-guard.sh [--check-only] <label>`;
  - exit 0 means ok, exit 3 means held with one reason line on stderr, exit 2 means bad usage;
  - call it once, without `--check-only`, right before the launch; `--dry-run` uses `--check-only`.
- Workers and solo sessions start through `claude-worker`, never plain `claude` (autocompact-children-1).
- Never symlink `node_modules`. Dependencies come from `ticket-deps.sh` only.

## Rulings (made while planning; Michael may overrule)

1. **A root with open children is refused in slice 3.** The refusal reads: "orchestrator Spaces arrive in slice 3b; drive it with trk-drive-program for now". The orchestrator path is in slice 3b.
2. **A solo root needs a repo checkout.** The first entry of `repos` that is a git checkout is the cwd. With none, `hx start` refuses and names `trk edit <root> --add-repo <path>`. Without a checkout there is no worktree.
3. **Worktree name:** the JIRA key in lower case (`proj-1234`) when `jira_url` has one, else the root id. That is the same name dispatch-ticket.sh would use, so an existing worktree for the ticket is reused.
4. **The skill is installed as a user skill.** `claude/skills/hx-work/` is symlinked to `~/.claude/skills/hx-work`, as the `trk` skill is. A full Claude Code plugin waits until slice 3b has two skills.
5. **`parent`** is the caller's `$TRK_SESSION`, else null. A pane id is never used: the scorecard joins `parent` to session uuids, and the row already has `pane` (sme-herdr-env, hx-s3-plan-1).
6. **Deferred minor M2 is fixed here** (`hx start` can leave a half-made Space). If a herdr call fails after the workspace exists, hx closes it and raises `StartError`. The CLI prints `hx start: <reason>` for `HerdrError` too, with no traceback.

## Review Focus

1. **Guard holds, or the script is missing:** `hx start` must create nothing and print the reason. It never launches past a missing guard.
2. **Shell quoting:** the launch line runs in a shell through `herdr pane run`. A model or effort outside the allowed patterns must be refused before anything is created. Root ids and JIRA keys are `[a-z0-9-]` after lowering.
3. **A herdr failure halfway through `start`:** no binding is saved, the workspace is closed, and the guard's recorded launch is not undone. That is acceptable: it costs a 30 s gap.
4. **An adopted session, or one hx did not start,** still gets null `parent`/`effort`/`reason` and the config model. Only the binding's own tab-1 session gets the launch values.
5. **The skill's asks go through `trk ask`,** so hx routes them. The skill must not block on AskUserQuestion for a gate decision.

- [ ] **Step 3: Implement.**
  - Order inside `start`:
    1. validate the root, role, checkout, model, effort and reason;

  - `cli.py`: `hx start <root> [--model M] [--effort E] [--reason TEXT] [--dry-run]`. Parent comes from the environment (Ruling 5). Catch `HerdrError` as well, with no traceback.

### Task 3: The `/hx-work` skill

**Files:**
- Create: `claude/skills/hx-work/SKILL.md`
- Test: `tests/test_skill.py`

**Interfaces:**
- Consumes:
  - the env `HX_ROLE=solo` and `HX_ROOT=<root>`, set by `hx start`;
  - `$TRK_SESSION`, exported by the user-wide trk hooks.

- [ ] **Step 1: Write the failing test** `tests/test_skill.py::test_hx_work_skill_names_the_flow`. It reads the file and asserts:
  - the frontmatter has `name: hx-work` and a `description:`;
  - the body contains `trk claim`, `--as worker`, `trk ask`, `/eng-toolkit:kickoff-ticket`, `/eng-toolkit:implement-ticket`, `/eng-toolkit:mark-ticket-for-verification` and `trk advance`;
  - the body does not contain `AskUserQuestion`;
  - the body is under 120 lines.

- [ ] **Step 2: Run** `.venv/bin/python -m pytest -q tests/test_skill.py`. Expected: FAIL (no file).

- [ ] **Step 3: Write the skill.** Load the `trk` skill first, and follow `mattpocock-skills:writing-for-agents`. The content, in this order:
  1. **Claim:**
     - `trk claim <root> --as worker --session "$TRK_SESSION" --json`;
     - exit 4 means another session holds it: say so and stop;
     - say that `trk-renew.sh` renews the lease each turn.
  2. **Read** `trk show <root> --json`. If it has a `jira_url`, take the key and use the eng-toolkit flow. Otherwise, work from the trk sections and criteria.
  3. **Gates:** follow `trk`'s stage gates, `framed → specd → built → merged → verified`. dispatch-ticket.sh's flow is the reference:
     - Framed/Spec'd: `/eng-toolkit:kickoff-ticket <KEY>`.
     - Built/Merged: `/eng-toolkit:implement-ticket <KEY>`, then the evidence rows and `trk advance` as the `trk` skill says.
     - Verified: `/eng-toolkit:mark-ticket-for-verification <KEY>`, then the verified evidence and `trk advance --outcome`.
     - Do not restate those skills; call them.
  4. **When a person must decide:** `trk ask <root> "<title>" --to <product|engineering> --question - --as worker --session "$TRK_SESSION"`, then end the turn. hx delivers the ask and wakes this pane with the answer. An in-pane `## ⚑ Needs you` from a eng-toolkit skill is fine as well.
  5. **Scope:** a solo session never starts other sessions. If the work needs children, open an `engineering` ask instead (orchestrators arrive in slice 3b).
  6. **Done:** the final `trk advance` closes the root. hx closes the Space 10 minutes after the root closes and the pane is idle. Write the `resolution` section first.
